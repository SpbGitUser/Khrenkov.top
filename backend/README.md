# Khrenkov.top Backend

ASP.NET Core 8 API: авторизация, загрузка, удаление, скачивание файлов и публичные ссылки. SQLite хранит метаданные; содержимое файлов остаётся в `Uploads`.

## Проекты

- `Khrenkov.top` — HTTP API, конфигурация приложения, команды управления БД и работа с файловой системой.
- `Khrenkov.top.Data` — отдельная библиотека: `ApplicationDbContext`, сущности в `Entities`, EF-миграции в `Migrations`, перенос старой базы и однократный импорт файлов.
- `Khrenkov.top.Tests` — интеграционные тесты с настоящей SQLite, временными файлами, HTTP-запросами и запуском команд отдельным процессом.

Контроллеры получают scoped `ApplicationDbContext` и обращаются к `DbSet` через LINQ, `SaveChangesAsync`, `ExecuteUpdateAsync` и `ExecuteDeleteAsync`. Контекст живёт в пределах запроса; одновременно несколько запросов его не разделяют. SQL-сервисы удалены. `FileStorage` отвечает только за файловые пути и общую блокировку изменений файлов. Ручной SQL остался только для распознавания старой схемы и регистрации её в истории EF при переходе.

## Первый локальный запуск

Команды ниже выполняются из корня репозитория:

```powershell
dotnet run --project backend/Khrenkov.top --no-launch-profile -- database migrate
dotnet run --project backend/Khrenkov.top
```

Обычный запуск **не применяет миграции**. Если база отсутствует, схема устарела или первоначальный импорт не завершён, приложение остановится с указанием выполнить `database migrate`. После ручного отката следующий запуск не вернёт схему обратно.

Путь по умолчанию — `Data/application.db` относительно content root веб-приложения, локально `backend/Khrenkov.top/Data/application.db`. Его можно заменить настройкой `Database:Path`, переменной окружения `Database__Path` или аргументом `--Database:Path`. Для запуска опубликованного приложения из другого каталога явно передавайте `--contentRoot <каталог-бэкенда>`.

## Контекст и сущности

| DbSet | Сущность | Таблица и назначение |
| --- | --- | --- |
| `Files` | `FileEntity` | `Files`: `Id`, уникальное `Name`, `Size`, `ModifiedUtc` |
| `ShareLinks` | `ShareLinkEntity` | `ShareLinks`: `Token`, `FileId`, `RemainingDownloads`, `CreatedAtUtc`; навигация `File` |
| `DataMigrations` | `DataMigration` | `SchemaMigrations`: совместимый со старой базой журнал первоначального импорта |

История **схемы EF Core** хранится отдельно в `__EFMigrationsHistory`. `SchemaMigrations` сохраняет прежние записи `1 InitialSchema` и `2 ImportExistingFiles`, чтобы переход не восстанавливал уже использованные ссылки из старого JSON.

Времена записываются в UTC в прежнем формате ISO 8601. Ограничения запрещают пустые имена, отрицательные размеры и лимиты. Внешний ключ `ShareLinks.FileId` удаляет связанные ссылки при удалении файла. Перезапись файла сохраняет `Id` и действующие ссылки.

SQLite работает с WAL. Рядом с `.db` могут находиться `.db-wal` и `.db-shm`; работающий процесс должен иметь доступ на запись в каталог. Путь БД внутри `Uploads` запрещён. `_shares.json` нельзя скачать, удалить, перезаписать или опубликовать через API.

## Применение миграций и импорт

```powershell
dotnet run --project backend/Khrenkov.top --no-launch-profile -- database status
dotnet run --project backend/Khrenkov.top --no-launch-profile -- database migrate
```

`migrate` только повышает схему до последней доступной версии. Команда завершается без HTTP-сервера, при ошибке возвращает ненулевой код.

1. Для базы прежней реализации проверяется журнал `SchemaMigrations` и ожидаемые столбцы. Проверенная исходная схема регистрируется как уже применённая `InitialSchema` в истории EF. Строки, идентификаторы, токены и текущие остатки скачиваний сохраняются. Неизвестные версии отклоняются.
2. `Database.MigrateAsync()` применяет недостающие EF-миграции. Первая миграция `InitialSchema` содержит `Up` для создания таблиц и `Down` для удаления.
3. Если нет записи об импорте версии 2, `LegacyDataImporter` через сущности контекста регистрирует существующие файлы и переносит активные ссылки из `_shares.json`. Данные и отметка завершения фиксируются в одной транзакции.

Импорт просматривает только непосредственно файлы в `Uploads`, исключая `_shares.json`. Сохраняются реальные размеры, время изменения и прежние токены, положительные остатки и время создания ссылок. Исчерпанные ссылки и ссылки на отсутствующие файлы пропускаются. На Windows имена сопоставляются без учёта регистра, на Linux регистр имеет значение.

Старый JSON не изменяется и после успешного импорта больше не используется. Некорректный JSON, неверная запись или дублирующиеся активные токены приводят к ошибке и откату транзакции импорта. Исправьте источник и снова выполните `database migrate`: созданная схема сохранится, незавершённый импорт повторится. Если импорт уже выполнен, повтор команды не добавляет старые ссылки и не возвращает использованные лимиты.

## Откат отдельно от применения

Остановите приложение и сохраните резервную копию перед откатом. Вызывайте команду из версии, которая ещё содержит `Down` откатываемых миграций.

```powershell
# Оставить заданную миграцию применённой, откатить более новые.
dotnet run --project backend/Khrenkov.top --no-launch-profile -- database rollback --to InitialSchema

# Откатить всю схему приложения.
dotnet run --project backend/Khrenkov.top --no-launch-profile -- database rollback --to 0
```

Можно передать имя или полный идентификатор миграции. `rollback` вызывает EF `IMigrator` с целевой версией и выполняет `Down`. Неизвестная цель и цель, для которой нужно сначала применить миграции, отклоняются. Команда не выполняет импорт и не запускает HTTP. Сейчас схема состоит из одной EF-миграции, поэтому `--to InitialSchema` ничего не меняет; частичный откат станет полезен после добавления следующих миграций.

**`--to 0` удаляет таблицы приложения, все метаданные, ссылки и отметку импорта.** Загруженные файлы и исходный JSON остаются. Повторный `migrate` создаст таблицы и выполнит первоначальный импорт заново; он не восстановит новые ссылки и может вернуть старые лимиты из JSON. Для сохранения состояния ссылок восстанавливайте согласованный бэкап, а не пересоздавайте базу.

Импорт из файлов — отдельная транзакционная операция с журналом завершения, а не EF-миграция, зависящая от окружения сервера. Отдельного `Down` для импорта нет: удаление только импортированных строк позднее могло бы удалить данные, уже используемые пользователем. Полный откат схемы удаляет их вместе со всеми остальными строками.

После отката приложение остаётся остановленным до выбора совместимой версии. Обычный запуск проверит схему; следующий **деплой**, напротив, явно выполнит `migrate` и снова применит доступные миграции.

## Добавление следующей миграции

Измените сущности/конфигурацию в проекте `Khrenkov.top.Data`, затем выполните из корня:

```powershell
dotnet tool restore
dotnet ef migrations add AddYourChange --project backend/Khrenkov.top.Data --startup-project backend/Khrenkov.top.Data --output-dir Migrations
dotnet ef migrations has-pending-model-changes --project backend/Khrenkov.top.Data --startup-project backend/Khrenkov.top.Data
```

Локальный инструмент `dotnet-ef` закреплён в `.config/dotnet-tools.json`. Просмотрите сгенерированные `Up`, `Down` и snapshot; проверьте применение и откат на отдельной базе. Уже применённые миграции не редактируйте. Для реального применения используйте команды приложения `database migrate`/`rollback`: они учитывают настройку пути, старую схему и импорт; прямой `dotnet ef database update` эти шаги не выполняет. Фабрика design time нужна для генерации модели без запуска веб-приложения.

## Согласованность с файлами

При обычном старте, после проверки схемы, каталог сверяется с диском через `DbContext`: добавляются/обновляются метаданные и удаляются записи отсутствующих файлов с их ссылками. Подключите или восстановите правильный `Uploads` **до запуска**. Внесённые вручную изменения файлов учитываются при перезапуске.

Загрузка сначала записывается во временный подкаталог `.upload-<случайный идентификатор>`. Затем файловая операция и изменение сущности выполняются под общей блокировкой одного процесса. При удалении сначала удаляется файл, затем запись БД. Отмена HTTP-запроса учитывается до изменения файла; после изменения запись метаданных завершается независимо от отключения клиента. Общей транзакции между SQLite и файловой системой нет; следующий старт исправляет расхождения после сбоя. Остатки временных загрузок можно убрать при остановленном приложении.

Остаток публичной ссылки уменьшается атомарно в короткой транзакции до отправки файла. Отсутствующий файл не расходует лимит; обрыв передачи его не возвращает. Блокировка загрузки/удаления рассчитана на текущий деплой одного процесса с общим `Uploads`.

## Проверки и публикация

```powershell
dotnet test backend/Khrenkov.top.sln --configuration Release
dotnet publish backend/Khrenkov.top/Khrenkov.top.csproj --configuration Release --runtime linux-x64 --self-contained true --output .tmp/publish
```

Тесты работают в отдельных временных каталогах и не меняют рабочую БД. Runtime-база и локальные загрузки исключены из публикации. Библиотека `Khrenkov.top.Data` с EF-миграциями включается в релиз. Dockerfile рассчитан на build context `backend` и копирует оба проекта перед restore. Для контейнера также сначала выполните `database migrate` с теми же постоянными томами и конфигурацией, затем запускайте HTTP.

## Резервное копирование

Для простого согласованного бэкапа остановите сервис и скопируйте весь каталог `Data`, включая оставшиеся служебные файлы, и `Uploads` в один набор. Не копируйте только основной `.db` во время работы: новые транзакции могут находиться в WAL. Для снимка БД без остановки используется SQLite Backup API; согласованность с загруженными файлами требует отдельного решения.

Восстанавливайте базу и файлы при остановленном сервисе, затем проверьте права и запустите совместимую версию приложения. Откат миграции меняет схему и не заменяет восстановление данных из бэкапа.
