# Khrenkov.top Backend

Backend-часть проекта находится в `Khrenkov.top` и содержит ASP.NET Core 8 API для авторизации, загрузки, удаления, скачивания файлов и публичных share-ссылок.

## Запуск

```powershell
dotnet run --project Khrenkov.top/Khrenkov.top.csproj
```

Если запускать из корня репозитория:

```powershell
dotnet run --project backend/Khrenkov.top/Khrenkov.top.csproj
```

По умолчанию backend поднимается на `http://localhost:5214`.

## SQLite и структура данных

Бэкенд использует SQLite через `Microsoft.Data.Sqlite`, с обычными параметризованными SQL-запросами. Отдельный сервер БД и ORM не нужны. При первом запуске создаётся файл `backend/Khrenkov.top/Data/application.db`. Путь по умолчанию отсчитывается от content root приложения; его можно заменить параметром конфигурации `Database:Path` или переменной окружения `Database__Path`.

| Таблица | Назначение |
| --- | --- |
| `Files` | `Id`, уникальное `Name`, `Size` в байтах, `ModifiedUtc` — метаданные загруженных файлов |
| `ShareLinks` | Первичный ключ `Token`, внешний ключ `FileId`, `RemainingDownloads`, `CreatedAtUtc` |
| `SchemaMigrations` | Версия, имя и время применения каждой миграции |

Содержимое файлов хранится в `Uploads`, а не в БД. Поля времени записываются в UTC. Размер и остаток скачиваний не могут быть отрицательными. При удалении записи файла БД удаляет связанные ссылки через внешний ключ `ON DELETE CASCADE`. Перезапись содержимого файла обновляет метаданные без смены его `Id` и сохраняет действующие ссылки.

SQLite использует WAL (журнал предзаписи). Рядом с `.db` могут появляться файлы `.db-wal` и `.db-shm`: это служебные данные SQLite, их нельзя удалять у работающего приложения. Пользователю процесса нужны права записи в каталог БД. Путь базы внутри `Uploads` запрещён; старый `_shares.json` также закрыт для скачивания, удаления, выдачи ссылок и перезаписи через API.

## Миграции и перенос существующих данных

Миграции запускаются автоматически в `Program.cs` **до начала обслуживания HTTP-запросов**, в том числе после деплоя. Runner находится в `Data/ApplicationDatabase.cs`.

1. **`001 InitialSchema`** выполняет SQL из `Data/Migrations/001_InitialSchema.sql`: создаёт таблицы, ограничения и индекс ссылок по файлу.
2. **`002 ImportExistingFiles`** выполняет `Data/Migrations/ImportExistingFiles.cs`: обходит непосредственно файлы в `Uploads`, записывает имена, реальные размеры и время изменения, затем переносит ссылки из старого `_shares.json`. Подкаталоги и сам JSON в пользовательский каталог БД не попадают.

Существующие токены, положительные остатки и время создания сохраняются. На Windows имя ссылки сопоставляется с фактическим именем файла без учёта регистра; на Linux регистр сохраняет значение. Тот же принцип используется при загрузке, скачивании, создании ссылок и удалении. Исчерпанные ссылки и ссылки на отсутствующие файлы пропускаются; в журнал записывается количество импортированных и пропущенных записей без токенов. Отсутствие JSON нормально для новой установки. Повреждённый JSON, некорректная запись или дублирующиеся активные токены прерывают импорт и запуск приложения с диагностикой.

Каждая миграция и запись о её завершении фиксируются в одной транзакции. При ошибке текущая миграция откатывается; уже завершённая миграция схемы остаётся. Исправьте исходные данные и перезапустите приложение: незавершённая миграция повторится. При успешном повторном старте применённые версии пропускаются, файлы не дублируются, а старый JSON не восстанавливает израсходованные лимиты.

Старый JSON сохраняется без изменений и после успешного импорта больше не используется приложением. Перед первым деплоем с БД сделайте резервную копию `Uploads`, включая JSON. Не удаляйте базу ради повторного импорта: это потеряет новые ссылки и может вернуть старые лимиты. Для будущих изменений добавляйте новую версию миграции; уже применённые миграции не редактируйте.

После миграций при каждом старте каталог сверяется с диском: добавляются/обновляются метаданные существующих файлов и удаляются записи отсутствующих вместе с их ссылками. Поэтому восстановить или подключить нужный `Uploads` следует **до запуска** приложения. Для файлов, добавленных вручную в обход API, выполните перезапуск, чтобы обновить каталог.

Загрузка сначала сохраняется в отдельный временный подкаталог `.upload-<случайный идентификатор>`, затем готовый файл заменяет целевой и регистрируется в БД. При удалении сначала удаляется файл, затем его метаданные. Файловая система и SQLite не образуют общую транзакцию: при сбое между этими действиями следующий старт сверит метаданные с диском. Незавершённые файлы в таких подкаталогах не выдаются через API; после аварийного завершения их можно убрать при остановленном приложении.

Лимит публичной ссылки уменьшается в короткой транзакции до отправки файла. Параллельные обращения не могут расходовать один остаток дважды. Отсутствующий на момент проверки файл не расходует лимит. Подтверждение получения всех байтов клиентом в этот механизм не входит; обрыв передачи не возвращает лимит.

Завершение загрузок и удаления последовательно выполняются через общий `SemaphoreSlim` в одном экземпляре приложения: файловая операция и обновление каталога не могут перемешаться между такими запросами. Передача загружаемых байтов во временный файл происходит вне этой блокировки. Это согласуется с текущим деплоем одного процесса; одновременную работу нескольких процессов с общим `Uploads` этот механизм не координирует.

## Проверка и публикация

Из корня репозитория:

```powershell
dotnet test backend/Khrenkov.top.sln --configuration Release
dotnet publish backend/Khrenkov.top/Khrenkov.top.csproj --configuration Release --runtime linux-x64 --self-contained true --output .tmp/publish
```

Интеграционные тесты используют настоящие SQLite-файлы и HTTP API, но работают в отдельных временных каталогах. Рабочие `Uploads` и БД проекта не меняются. Runtime-база и загруженные файлы исключены из публикации; SQL первой миграции встроен в сборку.

## Резервное копирование

Для простого согласованного бэкапа остановите сервис, скопируйте **весь каталог Data**, включая оставшиеся служебные файлы, и `Uploads` в один набор резервной копии, затем запустите сервис. Не копируйте только основной `.db` во время работы: новые транзакции могут находиться в WAL. Для бэкапа без остановки нужен SQLite Backup API и отдельно продуманный согласованный снимок загруженных файлов.

Восстановление выполняется при остановленном сервисе: верните согласованный набор `Data` и `Uploads`, восстановите права пользователя сервиса, затем запустите совместимую версию приложения. Автоматического отката схемы к старому релизу нет; перед первым использованием SQLite и будущими изменениями схемы сохраняйте бэкап.
